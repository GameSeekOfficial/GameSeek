## Summary

On 13 June 2026, monitoring showed an unauthorized attempt against administrative API routes. The activity was contained the same day.

The caller used automated reconnaissance against administrative paths and completed one GET request. That response contained a limited administrative user mapping: usernames, email addresses, and public metadata. The export was about 1.2 MB.

### Not exposed

The following were not in the exported data:

- Password hashes
- Authentication secrets
- Payment information
- Billing records
- Client IP addresses
- Session tokens
- Infrastructure credentials

Password hashes sit in a separate authentication store. The affected administrative routes cannot read them.

The vulnerable path was removed. Production was reviewed, hardened, and checked after the change.

## Timeline

### Detection

Monitoring flagged unusual requests under `/api/admin/*`.

The caller enumerated administrative routes. Some of those routes could be reached before session checks ran at the edge of the request, even though later code did perform authorization.

The successful request was a single administrative GET. It returned administrative usernames, administrative email addresses, and public metadata. It did not return credentials.

### Containment

Backend services were stopped to cut off the active path:

```bash
systemctl stop gameseek
```

The source address `89.16.12.67` was blocked at the host firewall with nftables, UFW, and iptables, so further connections from that host failed while the review was open.

### Cause

The failure was broken object-level authorization together with missing function-level access control.

Some branches of route handling ran before session validation finished. Deeper checks existed, but they ran too late in the request.

## Remediation

### Administrative routes

A single check now runs at the application entry, before any administrative handler:

```python
if path.startswith("/api/admin/") and not (
    session.is_owner()
    or session.has_valid_admin_token()
):
    return emit_rejection(
        status=403,
        error="Access denied. Request logged."
    )
```

Requests under `/api/admin/` continue only when the session is an owner session or carries a valid admin token. Everyone else receives HTTP 403, and the denial is logged. The database is not touched for a rejected request.

### Network

- Administrative SSH no longer listens on the default port, which cuts down automated scanning.
- nftables and UFW keep block rules across reboots, so a known bad host is dropped before it reaches the application.

### Automated blocking

Fail2Ban watches the API. A host that produces too many HTTP 403, 404, or 501 responses is banned.

```ini
[gameseek-api]
enabled   = true
filter    = gameseek-api
maxretry  = 10
findtime  = 60
bantime   = 172800
```

The window is 60 seconds. A ban lasts 172800 seconds (48 hours). This is aimed at scrapers, credential stuffing, and route enumeration.

## Checks after the fix

| Area | Result |
| --- | --- |
| Administrative routes | Unauthenticated calls receive HTTP 403 |
| Firewall | Known bad hosts are dropped before the app |
| Sessions | Validation runs for the administrative surface, and rejected calls never reach the handler |
| Monitoring | Events are logged, alerts are on, and the automatic ban path works |

## Current posture

Production now has:

- One authorization gate for administrative routes
- A tighter network edge
- Automatic bans for abusive API traffic
- Ongoing monitoring
- A written check after the incident

No active indicators of compromise remained at the time of this report.
